# 阶段四改进报告：`geo.height_band` 的假验证修复（高度带物化算子）

## 0. 一句话结论

文档里给业务侧看的 `geo.height_band(...)` 写法，此前存在一条**假验证**路径：
编译报成功、`Intersects` 状态显示 `verified`，而高度带**从未进入 Geo-IR**。
本版把它登记为 `HeightBand` 物化算子，三种写法（模块顶层 / 函数体内 / 内联）
都进 Geo-IR，并顺带闭合了"第 6 类失败从用户源码无法触发"这个缺口。

- 测试：`380 passed`（基线 330 + 新增 50），0 failed；新增文件 `tests/test_height_materialize.py`
- 示例：`examples/altitude_band.py`（新增），五个示例全部 `exit=0`
- 验证环境：WSL2 + Python 3.11.16 + `spu 0.9.5` + `jax 0.4.34` + `numpy 1.26.4`

---

## 1. 缺陷是什么：同一种文档写法，三种不同结果

`README.md` §7.1.1、`examples/vertical_conflict.py` 的 docstring、
`geo_privacy/core.py` 的 docstring 都把 `geo.height_band(...)` 写成
**用户可写的业务代码**。实测（改动前）：

| 用户写法 | 实测结果 |
|---|---|
| `route = geo.height_band(...)` 在**模块顶层** | `exit=0`，PSI `verified`，但高度带**被静默忽略**，只留 `GEO_INPUT_UNRESOLVED` 告警 |
| `band = geo.height_band(...)` 在**函数体内** | `exit=1`，`GEO_OP_UNSUPPORTED` |
| `geo.intersects(geo.height_band(...), other)` **内联** | `exit=0`，PSI `verified`，但该实参按 `SECRET` 计入且不受支持 |

第一行最危险：**它看起来完全成功**。状态表显示 `verified`，而"高度带参与判定"
这件事根本没有发生——判定退化成"整条航线格网集合 vs 管控区格网集合"，
高度信息丢失是静默的。这正是本项目 `AGENTS.md` 里"宁可留空，不给假数据"
要挡的那一类结果：不是缺功能，是给出可信外观的错误结论。

复现（改动前，模块顶层）：

```
parse_ok:  True
ops:       []            ← 零个算子进入 Geo-IR
inputs:    {}
diags:     []            ← 连告警都没有
```

## 2. 三处根因

| # | 根因 | 证据 |
|---|---|---|
| 1 | **方言表缺登记**：`GEO_OPERATIONS` 只有 6 个算子，而 `_GeoFacade` 暴露 8 个方法，差集正是 `['height_band', 'quantize']` | `geo_privacy/geo.py` vs `frontend/dialect.py` |
| 2 | **纠错建议为空**：`suggest_ops("height_band") -> []`，而 `suggest_ops("buffer_zone") -> ['Contains']`。用户写错名字会拿到"不支持"却**没有任何替代算子** | `semantic/semantics.py::ALIAS_TABLE` |
| 3 | **模块顶层语句从不被遍历**：`FrontendAnalyzer` 是 `ast.NodeVisitor`，但既无 `visit_Module` 也无 `generic_visit`；`visit_FunctionDef` 直接 return，`_analyze_function` 只走 `function.node.body` | `frontend/analyzer.py` |

第 3 条是"假验证"的直接成因：模块顶层的 geo 调用**连诊断通道都没有**。

## 3. 修法（按"最小且可验证"取舍）

### 3.1 登记为**物化算子**，而不是"也行"或"只写文档"

两条候选路线：**(A)** 登记为方言算子；**(B)** 只把它文档化为"仅明文预处理"。
选 **(A)**，并把文档同步成实际可编译的形态。理由：

- 高度带**已经**通过 `CellSet.from_height_band` 在明文侧跑通（实测
  `route` 11 层 / `zone` 3 层 / 交集 3），语法与语义都成立；
- 登记后它进入 Geo-IR 与代价账，`plaintext-local` 这个状态词把
  "没有密态执行"变成**显式结论**而不是静默省略；
- 若选 (B)，用户照着现有文档写仍然会踩中假验证，只是把坑从代码挪到文档。

### 3.2 新增 `materializes` 方言属性

`DialectEntry` 增加 `materializes / value_params / config_params /
required_params / defaults`，并在 `_emit_operation` 里分流到
`_emit_materialize`。关键设计取舍：

- **被编码的数据（x, y）进 `inputs`**，**物化配置（高度带 / 层级）进 `params`**。
  理由：敏感度判定只看 `inputs`；把 `level=15` 混进去会让公开的编码参数
  参与密态需求判定。
- **产出敏感度由 `inputs` 推导，不写死**。这是本版自己的一个候选泄漏：
  初版写死 `PUBLIC`，若调用方把 x/y 标注为 secret，消费它的 PSI 算子会被
  判成"可走明文"。已改为 `self.program.input_sensitivity(operation)`。
- 位置实参与命名实参**都支持**：facade 签名顺序恰是
  `value_params + config_params`，位置写法在本方明文里本来就跑得通，
  拒绝它属误报。
- 配置参数**必须是编译期字面量**：层号决定格网码本身，运行期层号无法
  静态展开层集合。
- 登记时写 `height_level`，让第 6 类失败检查（`HEIGHT_LAYER_UNSUPPORTED`）
  能读到 `level` / `height_max`——此前该检查的这两个键**无人填充**，
  从用户源码根本无法触发。

### 3.3 加 `visit_Module`，但不 lint 脚手架

模块顶层改为显式下降。这里踩到并修掉了一个自己造成的误报：

- 最初把整条语句交给 `_visit_statement`，于是
  `if __name__ == "__main__":` 被判成 `DYNAMIC_CONTROL_FLOW`（**假错误**）。
- 改为 `_scan_module_statement`：只收方言调用，不报未识别调用（减少噪音）；
- 但**真正的运行期分支仍然被抓**：`if compute_flag():` 在模块层会被
  标进 `_inside_control_flow`，由 `validate_control_flow` 报第 4 类失败。
  判据放进 `_is_dynamic_module_control`：字面量与 `__name__` 这类
  解释器常量比较不算动态分支。

### 3.4 明文工具与算子分离

`geo.quantize` 是 facade 上的公开方法，返回普通标量，**不是算子**。
修 `visit_Module` 后它一度从"静默忽略"变成"`GEO_OP_UNSUPPORTED` 硬错误"——
同样是误报。新增 `PLAINTEXT_UTILITIES` 名单与 `GEO_PLAINTEXT_UTILITY` 诊断：
说明"不进 Geo-IR"，不阻塞编译。并加了一条**覆盖测试**：facade 上每个方法
必须归属于 算子 / 物化 / 明文工具 三者之一，不允许存在灰色地带
——`height_band` 出事时正是这种灰色状态。

### 3.5 下游阶段保持诚实

| 阶段 | 处理 |
|---|---|
| JAX 生成 | 物化算子不进 `skipped` 的"缺 JAX"叙事，单列明确原因 |
| SPU 能力核查 | 新增 `not-routed` 状态；既不谎称 `supported=True`，也不产生无关的 `SPU_UNSUPPORTED` 诊断 |
| SPU 模拟 | 不计入 `planned_but_not_jax`，而是"明文物化算子，不走密态路径" |
| 最终状态表 | 新增状态词 `plaintext-local`（用 `backend-direct` 会让人以为"有个密态后端没跑"；用 `planned` 则像未完成） |

### 4.3 第 6 类失败从用户源码可触发（此前不可触发）

```
[ERROR] HEIGHT_LAYER_UNSUPPORTED @ overflow.py:2:8
  算子 HeightBand 的高度带 [0, 1000] m 在层级 L=23 上需要 8 位层号，超出 Z7 位域
    原因: GB/T 40087-2021 附录 B 的层号上界随层级上升：L=23 时 hmax=1000 m 落在第 8 层，
          需要 8 位；64 位定长键的 Z 位段只有 7 位（上限 127）
    建议: 把层级降到 L<=22（该高度带在 L=22 上只需 7 位），或把高度带收窄到实际管辖区间
    预计代价: PSI / CompactCellSet（b=64, d=0, R=1）
```

四要素齐全（位置 / 原因 / 替代 / 代价），`level=22` 则无诊断。

### 4.4 对抗性检查（变异测试）

逐条把改动**回退**，确认新增测试确实会失败；每条变异后文件按字节还原。

| 变异 | 结果 |
|---|---|
| 移除 `visit_Module` | `16 failed` |
| 物化分支失效 / 被短路 | `12 failed` |
| 敏感度写死 `PUBLIC` | `9 failed` |
| 敏感度写死 `SENSITIVE` | `3 failed` |
| 类型推断退回只看位置实参 | `1 failed` |
| 模块层把所有 `Compare` 当动态分支 | `1 failed` |
| `HeightBand` 后端由 `Plaintext` 改 `PSI` | `2 failed` |
| 移除明文工具名单 | `2 failed` |

全部变异后文件 sha256 与改动后一致（byte-identical）。

> 首轮对抗有**三条变异存活**，暴露了我最初两个测试的真实弱点：
> (1) `__main__` 用例的守卫块内**没有算子**，对"是否把字面量比较当动态分支"不敏感；
> (2) 敏感度用例只把 `zone` 标 secret，未标 x/y，两条代码路径结论相同。
> 已补 `test_geo_call_inside_main_guard_...` 与改写敏感度用例；上述 9/1 failed 即复测结果。
> 第三条（别名）经核查是**语法冗余而非测试漏洞**：`"height"` 子串已覆盖
> `"height_band"`，且既有 `ALIAS_TABLE` 同样是这个风格，未作改动。

## 7. 下一步建议（按价值排序）

1. **PSI 结果链式传递**：让 `CellSetIntersect` 的交集本体成为下游算子的可解析输入，
   使"求交 → 属性聚合"能在一条密态链上完成，不必每步回明文。
2. **`Contains` 的密态子集比较**：把当前明文比较换成 MPC 基数比较，收掉 §7.6 的泄漏面。
3. **`L` 位域重划的资源评估**：给出 4→5 位（或 96 位 3D 码）的改造影响面与迁移代价，
   供接入层规范决策使用。
4. **K 的编译期实算**：`resolve_cost` 已支持按 K 实例化，但 K 目前需显式传入；
   从 IR 推断元素数可让 WeightedSum 的位宽报价不再依赖人工输入。
